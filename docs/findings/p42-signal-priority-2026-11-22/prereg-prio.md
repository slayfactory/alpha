### Поправка к §13.73.2 (PS-955): ось `prio` — приоритет кандидатов при нехватке мест (TK-679, В-172). Записана ДО счёта клеток оси.

## 1. Зачем

Владелец 22.11 (В-172): «новые признаки - в случае сделок которые потенциально близкие или совмещенные по таймингу - приоритет дается той монете у которой натр выше/обьем выше». По В-171 («это надо не отдельно а с чем то перебирать») — осью общего перебора, не отдельным исследованием.

Как сейчас (`breakout tick`, `run_tick_xb`): сигналы идут по порядку (время сделки-сигнала в мс, расстояние до уровня, монета по алфавиту, уровень); сигнал проходит проверки «уровень израсходован → монета занята → пауза монеты → общая пауза → потолок `p` = 3 позиции на сторону → вход по ленте». Кандидаты соперничают только за место под потолком `p`: кто раньше по времени, тот и вошёл; расстояние и алфавит решают лишь при совпадении времени до мс.

Верхняя граница (измерено до счёта на строках баз h775 со стопом 5 % — готовые `meta.json` TK-677; на базе' со стопом 3 % / 4 % число отказов «потолок» печатает шаг 0, рядом с этими): отказов «потолок» — лонг 0 / 0 / 23 (окна wa / wb / wc) на 1 222 сигнала и 574 сделки; шорт 8 / 1 / 0 на 675 сигналов и 435 сделок. При `p` = 3 правило приоритета может изменить не больше 23 решений лонга и 9 шорта (отвергнутый уровень может дать сигнал на следующей минуте, поэтому разных сделок ещё меньше).

Движок: ветка `bb/tk-679-signal-priority-v1-thr_zanyajgvz5` (SHA — в записи журнала), ключи портфеля `pr`, `pw`; при значениях по умолчанию (`pr=0 pw=0`) строка `params` и вывод прежние.

## 2. Ось (значения фиксированы до счёта)

Ключ оси — `prio` (класс «портфель»), составная из ключей движка:

- `pr` — кто берёт место: 0 — как сейчас (расстояние до уровня, монета по алфавиту); 1 — выше NATR(30) закрытой минуты `t−1`; 2 — выше оборот за 15 закрытых минут `t−15 … t−1`; 3 — выше оборот за 60 закрытых минут (`t` — минута сигнала; горизонты — по слову владельца 22.11 о масштабе сделки, 5–60 мин). Равенство — прежний порядок.
- `pw` — окно сбора кандидатов, мс. 0 — правило `pr` действует только среди сигналов с одним временем (мс). `pw > 0`: кандидат, прошедший проверки и занимающий последнее свободное место (открыто `p − 1` позиций), открывает окно `[t0, t0 + pw]`; прошедшие проверки кандидаты этого окна собираются; в `T = t0 + pw` проверки повторяются, кандидаты ранжируются по `pr` и входят, пока есть места; вход — по ленте на `T + lat` с прежними проверками (`stale`, `beyond`); кандидат, у которого сделка в `(сигнал, T]` дошла до уровня, снят. При двух и более свободных местах вход сразу, как сейчас. Уже открытая сделка не отменяется никогда; значения `pr` и NATR выхода кандидата — на минуте его сигнала.

| метка | `pr` | `pw`, мс | роль |
|---|---|---|---|
| `off` | 0 | 0 | база оси (обе стороны) |
| `d1`, `d5`, `d60` | 0 | 1 000 / 5 000 / 60 000 | контроль: окно с прежним порядком (цена задержки входа) |
| `n1`, `n5`, `n60` | 1 | 1 000 / 5 000 / 60 000 | выше NATR |
| `q1`, `q5`, `q60` | 2 | 1 000 / 5 000 / 60 000 | выше оборот за 15 мин |
| `h1`, `h5`, `h60` | 3 | 1 000 / 5 000 / 60 000 | выше оборот за 60 мин |

12 значений сверх базы. `pr = 1, 2, 3` при `pw = 0` в карту не входят: считаются только на шаге 0 как проверка (ожидание — 0 изменений, печатается счётчик).

Совместимость: `pw > 0` требует `ew > 0` (в базах `ew=5`) и несовместим с осями `mk`, `ek` (и `xb`) — эти пары пропускаются; остальные правила совместимости и допустимости клетки — §13.73.1. Недопустимые клетки отвергает разбор движка, стадия `validate`.

Потолок `p` в ось не входит: он меняет число позиций и набор сделок, а не порядок выбора. Ось `p` = {1, 2, 3} — отдельной поправкой TK-674; пара `prio` × `p` — обычная пара карты.

## 3. Чтение

- Действие правила приоритета — клетка (`pr` = k, `pw` = W) против контроля (`pr` = 0, `pw` = W) при том же `p`; цена окна — контроль против `off`. Победитель пары, прирост над базой', охраны — без изменений (§13.73.2).
- Числа — по правилу владельца: $ при ставке 500 $, Σ + среднее на сделку + число сделок, годовой Шарп по суткам, % маржи, просадка, перехай, база рядом с каждой строкой; месяцы и окна отдельно.
- m стороны = все клетки стороны в БД на момент чтения (вместе с этими); чтение — описательное, «найдено на этих данных».

## 4. Шаг 0: счётчики до карты (без P&L)

`tools/p42/tk679_run.py touch`: строки `p` ∈ {1, 2, 3} × `pr` ∈ {0, 1, 2, 3} × `pw` ∈ {0, 1 000, 5 000, 60 000} на базе' стороны (PS-955: стоп лонга 3 %, шорта 4 % — она же база карты), h775, три окна (48 строк на сторону, один проход сигналов на сторону и окно). Читаются только счётчики `meta.json` (отказы «потолок», окна, окна с ≥ 2 кандидатами, смены порядка, входы и отказы после окна) и ключ сделки (монета, уровень, время сигнала, время входа); столбцы денег не читаются и не печатаются. В том же проходе — 49-я строка `p=100000` (без потолка позиций, В-173) для описательного разбора кластеров сигналов: у него своя предрегистрация, на шаге 0 по этой строке читаются те же счётчики.

Мера «задето» значения (`pr` = k, `pw` = W) при данном `p`: число сделок, которых нет в одной из двух строк — этой и её контроля (`pr` = 0, `pw` = W, то же `p`), сумма трёх окон.

Правило (порог фиксирован до шага 0): значение `n*` / `q*` / `h*` входит в карту стороны при `p` = 3 только если «задето» ≥ 20 сделок (≈ 3,5 % сделок базы лонга, 4,6 % шорта); контроль `dW` входит вместе с хотя бы одним значением своего окна. Если ни одно значение не прошло — ось `prio` при `p` = 3 для стороны закрывается записью «правило не действует: задето N из M сделок», клетки карты не считаются. То же правило по строкам `p` = 1 и `p` = 2 решает, какие клетки пары `prio` × `p` считаются (после поправки об оси `p`). Одинаковые с контролем клетки в карту не идут и m не увеличивают.

Бинарь ветки TK-679 (md5 — в записи журнала). До шага 0: G-base — 6 строк баз (L, S × 3 окна) × 4 CSV байт в байт против готовых баз h775; при расхождении — стоп. Клетки без новых ключей не пересчитываются (бинарь добавляется в равные, `res/eqbins674.json`).
