### 2.5 Стена против ЦП: что известно о боевом режиме (замечание критика A2)

- **Юнит партии** `tk674c-quadsS3` за 10 465 с (19:44–22:38 UTC 24.11): ЦП 32 409 с = **3,10 ядра в среднем** (user 87 %, sys 13 %), `MemoryPeak` 35,4 ГБ = `MemoryMax` (в cgroup входит кэш страниц); за те же часы стена движка в 137 вызовах 6 266 с → до **5,2 ядра** внутри вызова; хост: load 14–16 на 8 vCPU (3–4 движка рядом).
- **Параллельная эффективность по логам** (поток-секунды фазы 2 «варианты» / стена фазы 2, из 200 рабочих `P42_WIDE` и 7 разрешений): тяжёлые 161, средние 48, лёгкие 8,8 потока в среднем; из них «ожидание суток и разрешения» 57 % (тяжёлые), 47 % (средние), 32 % (лёгкие) поток-секунд — ожидание держит разрешение чужому разбору суток, а не диск (§2.1 прежней версии: R = 7, D ≈ 0,1).
- **Минутки не масштабируются по потокам** (окно wa, 539 монет, хост занят, `results1.jsonl`): загрузка минуток 7,4 / 8,5 / 8,5 / 8,3 с по стене на 1 / 2 / 4 / 7 потоках при ЦП 12–13 с (user 3,3 + sys 9,7) — это последовательная часть вызова (ядро, копирование и обнуление страниц), 8,8 % стены партии, 22 % у лёгких.
- **Что не измерено и почему:** параллельная эффективность на **свободном** хосте («один движок за раз») — пока идёт партия, свободного хоста нет; её даёт A3 (полный тяжёлый вызов на пустом srv, окно после `tk674c-quadsS3`). Пока на свободной машине не измерено, оценки в часах стены даются в режиме **занятого хоста** (стена ∝ ЦП: каждая сэкономленная ЦП-секунда возвращается в общий пул), а ЦП-секунды — второй колонкой.

| Диск: `read_bytes` против `rchar` | ≤ 1,6 % (`majflt` 0, состояние потоков D ≈ 0,1) | «память вместо диска» уже есть: всё читается из кэша страниц; остаток — копирование и обнуление страниц ядром (рычаг h) |
| SHA-256 бинаря (`SigCache::open`, программный) | 0,15 % | потолок 0,15 % |
| `ZipSrc::day` | 0,2 % | см. e′ |

Сумма всех «мелочей» ≤ 1,3 % — по ним отдельный проход не делать.

## 4. Дублирование ходов и пред-компоновка веера

Термины: **тик** — сделка ленты (то, что читает `Cursor::next_tick`); **ход** — один проход `sim_tail_e` по тикам от входа до выхода одного лота одного варианта; **позиция** — результат варианта (строка `short-trades.csv`; у позиции из двух лотов два хода).

### 4.1 Что именно повторяется (код)

`run_tick_xb` (`tick.rs:3230`) идёт по сигналам варианта в порядке времени; принятый сигнал даёт решение о входе (`entry_decision` / `mk_decision` / `xb_decision` …), затем ход лота 1 (`sim_fill_lc_e`, `tick.rs:3433`) и, при `split`, решение и ход лота 2 (`sim_fill_lc_s`, `tick.rs:3500`). Исход принятого входа зависит от: ленты монеты после `entry_ms` (общая для всех вариантов), цены входа `p0` (функция ленты), `natr` и контекста уровня `lc` (функции сигнала), параметров выхода `ExitCfg`. Портфельное состояние варианта (`busy`, `cool_until`, `open`, `gstops`, `consumed`) решает только, **какие** входы принять, но не исход принятого → **исход = чистая функция** `f(монета, entry_ms, сторона, путь-параметры ExitCfg)`. Веер — «один фактор за раз» от базы (имена вариантов: `…+e2t2+…+w270`), поэтому большинство вариантов идут по одной ленте с почти одинаковыми параметрами.

### 4.2 Измерено

| Уровень | Что повторяется | Число | Метка |
|---|---|---|---|
| 1. Внутри вызова, между вариантами | один и тот же вход (монета, `entry_ms`) обходится разными вариантами. Мерный бинарь `ws-measure` (счётчики в `sim_tail_e`, поведение не менялось: хеш дерева вывода = базе) на H1: **97 596 ходов, 3 294 входа (29,6 хода на вход), 511 268 390 тиков в ходах; сумма максимумов длины по входу 24 259 224 тика → 21,1×** (ходы читают один и тот же участок ленты в 21 раз больше, чем длиннейший из них). Независимая оценка по времени удержания на клетке `p5cd4933c8e` (539 монет, архив, все варианты): 365 717 позиций → 10 440 входов, 35 на вход (медиана 5, максимум 1 465), Σ удержаний / Σ максимума на вход = **21,3×** — совпадает | 21,1× по тикам | изм. |
| 1б. Те же исходы | разных исходов (строка позиции целиком) 62 237 из 365 717 = **17 %**; по времени удержания **4,9×** → 80 % времени ходов повторяют исход, уже полученный другим вариантом с того же входа | 4,9× по времени | изм. |
| 2. Между вызовами одной стадии | клетки одного окна и стороны делят входы (разные куски веера на тех же сигналах): ⟦dup3: F2 по wc-S short / wc-L long / wb-S / wa-S⟧; пробный счёт на 12 первых архивах: ещё **3,5×** | ⟦F2⟧ | изм. |
| 3. Вся стадия | F12 = F1 · F2 (время удержания всех ходов / сумма максимумов по объединению входов) | ⟦F12⟧ | изм. |

Оговорки: (1) вес «время удержания» — прокси числа тиков (для 1 и 3 в ленте одной монеты число тиков пропорционально времени; подтверждено 21,1× по тикам против 21,3× по времени); (2) 21× — **потолок** общего ствола: каждый живой вариант всё равно вызывает `on_trade` / `fill_takes` на каждом тике своего хода (29,5 % ЦП на v1), общим становится только «обвязка» (`next_tick` + замыкание + цикл, 34,4 %); (3) тихие блоки (`ws_block_quiet`, строго 16 / 64 / 256 тиков): 94,1 % / 89,7 % / 81,8 % тиков лежат в блоках без событий — **не используется** (В-184: каждый тик виден стратегии), приведено только как контекст, почему `on_trade` почти всегда идёт по ветке «ничего не произошло».

### 4.3 Дизайн пред-компоновки (четыре ступени, от безопасной к рискованной)

| Ступень | Суть | Точность | Что экономит | Что нужно |
|---|---|---|---|---|
| A. Пучок (поток тиков один раз) | варианты, принявшие вход `(монета, entry_ms)`, идут в ногу по одному срезу ленты: выборка тика и фильтр `t > entry_ms` один раз, `on_trade` — у каждого варианта; исход каждого — прежняя чистая функция | байт в байт по построению (порядок вызовов на каждый вариант тот же) | «обвязку» хода: (1 − 1/N) её доли, N — вариантов в пучке (на H1 в среднем 29,6; медиана 5 на архиве клетки `p5cd4933c8e`) | внешний цикл по сигналам → внутренний по вариантам: портфели всех вариантов в памяти одновременно (≈ 13 КБ на вариант: `busy`, `cool_until`, `cpause_until`, `streak` по 539 монетам → ≈ 22 МБ на 1 705 вариантов); тот же порядок сигналов для всех вариантов даёт ещё и общую локальность суток (сейчас `store::decode` + ZSTD 9,8 % ЦП — перераскодировка суток при `--cap-gb` и разном порядке) — **гип.** |
| B. Память исходов по ключу пути | `HashMap<(монета, entry_ms, сторона, ключ пути), TickOut>` (с блокировкой по шардам, 7 потоков): первый вариант считает ход, остальные берут исход; ключ = все поля `ExitCfg`, которые ход читает (лот 1 не читает `w2`, `e2`, `e2t`, `s2` …; лот 2 читает свои) | точна, **если ключ полон**: пропуск поля даёт молчаливо неверный исход → гейт: дифф-тест случайных вариантов с «выключенной» памятью, дерево вывода 600 клеток, список полей получается статически (`grep` по чтению `ex.<поле>` в ходе) и подтверждается тестом «поле меняется — исход меняется» | целые ходы (не только обвязку): верхняя граница 4,9× по времени ходов (уровень 1б), реально — по полноте ключа (ключ строже равенства исходов) | список прочитанных полей и счёт различных ключей по `variants.txt` (дёшево, до кода) — **гип.** |
| C. Хранилище исходов между вызовами | то же, что B, но на диске / в БД (`/data/...`), ключ + «смысловая версия» кода хода; вызов берёт готовые исходы | как B + ключ версии: правка хода инвалидирует хранилище | уровень 2: ещё до ⟦F2⟧× (по вызовам одной стадии); в боевых вызовах ходы почти всех клеток стадии на одних и тех же входах | согласование с рычагом i (ключ по исходнику, иначе каждая подмена обнуляет и хранилище); размер ≈ позиций в стадии × 200 Б; память исходов ×1,3 по TK-683 (слабо) считалась на уровне 1б без F2 — **гип.** |
| D. Слияние состояний | варианты с равным `Pos` идут одним состоянием до расхождения параметров | требует знания «до какого момента» параметры не влияют → зависит от гипотез | вариант для критика и владельца | **не рекомендуется** (ломает «любая гипотеза»: новый параметр выхода должен сам объявлять момент расхождения) |

Ключ B / C — **автоматический «по умолчанию всё входит»**: производный хеш по всему `ExitCfg` минус явный список полей, не влияющих на ход (список под тестом «поле меняется — исход меняется / не меняется»); новое поле `ExitCfg` попадает в ключ само, пока его не внесли в список исключений → новая гипотеза не даёт молчаливо устаревших исходов. Режим проверки: на попадании ход всё равно считается и сверяется (в гейте 100 %, в бою — выборка), любое расхождение = ключ неполон = остановка.

Порядок при PASS: B (проще A в запуске: внешний цикл не меняется, общий словарь исходов на 7 потоков; точность — по полноте ключа и режиму проверки) → A на оставшихся различных ключах → C, если F2 подтвердится на боевых клетках. Каждая ступень — отдельный коммит, до / после на H1, хеш дерева = базе.

### 5.2 Стек

Разложение ЦП v1 на H1 (perf, §3.1): **S** — обвязка хода (`next_tick` 20,3 + `run_tick_xb` 14,1) = 0,344; **W** — `on_trade` + `fill_takes` (20,6 + 8,9) = 0,295; **R** — остальное (разогрев суток 9,8 + ядро + фаза 1 + минутки + запись) = 0,361. Формула: **итог = (S − e) / G · (1 − r) + W / G + R** — рычаг e уменьшает обвязку, память исходов B делит стоимость всех ходов на G, пучок A снимает долю r оставшейся обвязки (общий ствол считается только для различных ключей). Для боевой смеси доли ходов умножены на 0,889 (фаза 2 = 78,2 % стены × доля ходов 72,6 % = 56,8 % против 63,9 % на H1); скрипт — `tools/p42/tk706/stack_model.py`.

| Сценарий (e / G / r) | H1: ЦП v1 = 1 | H1: к боевому `l` | Боевая смесь: к боевому `l` |
|---|---|---|---|
| консервативно (0,08 / 1,0 / 0,5): память исходов не помогла, пучок наполовину | 0,79 (×1,27) | 0,60 (**×1,66**) | 0,64 (**×1,56**) |
| ожидаемо (0,11 / 2,0 / 0,5) | 0,57 (×1,76) | 0,43 (**×2,3**) | 0,49 (**×2,1**) |
| верхняя граница (0,15 / 4,9 / 0,9) | 0,43 (×2,35) | 0,33 (**×3,1**) | 0,39 (**×2,6**) |

Вывод для вопроса владельца «было 100 мс на круг, стало 15 мс»: по этой модели прирост на тяжёлых вызовах — **×1,7 (консервативно) … ×2,3 (ожидаемо) … ×3,1 (потолок)** к боевому `l`; ×6–7 недостижимо одними ходами: после всех рычагов остаётся R (≈ 36–43 % ЦП v1: разогрев суток, ядро на страничных ошибках, фаза 1 и минутки) — следующая стена. Её режут отдельные оси: C (готовые исходы между вызовами → ходы не считаются вообще), h (минутки один раз на партию), i (подмена без промаха кэша), и PGO / LTO на самом R.
Цена подмены бинаря: первая партия на «промахе» кэша сигналов (+31–33 ЦП-с на H1, ≈ +20 % стены партии по модели §2.4) → собрать всё сборочное и кодовое одной подменой (рычаги a, d, e, B, A).

## 6. Риски и вопросы критику

1. **Полнота ключа B / C.** Пропущенное поле `ExitCfg` в ключе = молчаливо неверный исход. Защита: ключ «по умолчанию всё входит» + список исключений под тестом + режим проверки (100 % в гейте). Достаточно ли режима проверки на 600 клетках как доказательства, и нужен ли выборочный контроль в бою?
2. **Пучок A против параллелизма.** Сегодня 7 потоков идут по разным вариантам; пучок требует внешнего цикла по сигналам и внутреннего по вариантам (портфели всех вариантов в памяти ≈ 22 МБ). Если делить варианты по потокам, размер пучка падает ≈ в 7 раз (29,6 → ≈ 4,2 на H1) и выигрыш A падает. Рабочее решение — B сначала (не меняет внешний цикл), A только на остатке; критик: ждёт ли нас здесь ловушка с порядком обработки портфеля (решение по сигналу зависит от выходов того же варианта, значит ход нельзя отложить)?
3. **Согласование с В-184.** B и C не вызывают `on_trade` на тиках ходов, чей исход уже получен другим вариантом с **тем же** ключом — это повторное использование равного вычисления, а не пропуск тика под гипотезу; новая гипотеза = новое поле = новый ключ автоматически. Подтвердить, что такое чтение В-184 допустимо (если нет — остаются A, e, сборка: ×1,6 к `l` по модели, строка «консервативно» при G = 1).
4. **Репрезентативность H1.** 90 монет из 539, один вариант веера (p5cd4933c8e, 1 705 вариантов); дублирование на 539 монетах по архиву — 21,3× против 21,1× на H1, совпадает; на лёгких вызовах (средние / лёгкие 45 % стены) выигрыш ходов меньше — отражено множителем 0,889, не измерено.
5. **Что не посчитано `ws-measure`.** Счётчик стоит только в `sim_tail_e`; тики решений о входе (`entry_decision`, `mk_decision`, `xb_decision`, `lot2_decision_d`) не считаются — по профилю это ≈ 2–4 % ЦП (`lot2_decision_d` 1,7 % на живом вызове), в модель не вошло.
6. **PGO и обучающая выборка.** Обучение на H1 и замер на H1 завышает прирост; контроль — тот же бинарь на другом окне (`--window wb`) ⟦hold-out⟧. Бинарь PGO привязан к дереву исходников: любая правка кода хода после обучения требует нового обучения.
7. **Шум.** 4–8 % повтор-повтор: выводы по −23,5 % (a) и счётчикам железа надёжны; −1,2 % (b) — в шуме, не используется как довод ни за, ни против.
8. **Ключ кэша сигналов по исходнику (i).** Экономит промах на каждой следующей подмене, но ослабляет защиту «любое изменение бинаря сбрасывает кэш»: правка кода сигналов вне хешируемых файлов даёт молчаливо устаревшие сигналы. Делать только с тестом «исходник сигналов изменился → ключ изменился» и только если ожидаются ≥ 2 подмен после первой.
9. **Гейт.** Хеш дерева вывода H1 (10 203 файла) — быстрая проверка рычага, не замена `tools/p42/tk683_gate.py` (≈ 600 клеток c539) и `vps-check.sh … all` перед подменой.
