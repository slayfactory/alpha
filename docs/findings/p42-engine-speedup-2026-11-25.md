### 2.5 Стена против ЦП: что известно о боевом режиме (замечание критика A2)

- **Юнит партии** `tk674c-quadsS3` за 10 465 с (19:44–22:38 UTC 24.11): ЦП 32 409 с = **3,10 ядра в среднем** (user 87 %, sys 13 %), `MemoryPeak` 35,4 ГБ = `MemoryMax` (в cgroup входит кэш страниц); за те же часы стена движка в 137 вызовах 6 266 с → до **5,2 ядра** внутри вызова; хост: load 14–16 на 8 vCPU (3–4 движка рядом).
- **Параллельная эффективность по логам** (поток-секунды фазы 2 «варианты» / стена фазы 2, из 200 рабочих `P42_WIDE` и 7 разрешений): тяжёлые 161, средние 48, лёгкие 8,8 потока в среднем; из них «ожидание суток и разрешения» 57 % (тяжёлые), 47 % (средние), 32 % (лёгкие) поток-секунд — ожидание держит разрешение чужому разбору суток, а не диск (выборка состояний потоков, абзац ниже: R = 7 всё время, D ≈ 0,1).
- **Минутки не масштабируются по потокам** (окно wa, 539 монет, хост занят, `results1.jsonl`): загрузка минуток 7,4 / 8,5 / 8,5 / 8,3 с по стене на 1 / 2 / 4 / 7 потоках при ЦП 12–13 с (user 3,3 + sys 9,7) — это последовательная часть вызова (ядро, копирование и обнуление страниц), 8,8 % стены партии, 22 % у лёгких.
- **A3 — измерено 25.11 на свободном srv** (`bench/results11.jsonl`; один тяжёлый вызов: 539 монет, 1 705 вариантов, 7 потоков, `--cap-gb 24`, `P42_WIDE=200`; хеш дерева вывода у базы и `v1-lto` = `55dfa1c8a03cd588`): **попадание кэша сигналов** — стена 63,1 → 46,8 с (**−25,8 %**), ЦП 345,5 → 254,4 с (−26,4 %), sys 36,8 → 28,8 с; **промах** — стена 100,0 → 94,3 с (**−5,7 %**), ЦП 512,1 → 464,1 с (−9,4 %); RSS 12,6 ГБ (попадание) / 27,9 ГБ (промах). Ядер в среднем (ЦП / стена): база 5,5 → `v1-lto` 5,4 (попадание), 5,1 → 4,9 (промах) — на свободном хосте один вызов использует ≈ 5 из 7 потоков, LTO параллельность не меняет. Выигрыш стены = выигрыш ЦП на попадании; на промахе (первый вызов после подмены бинаря платит пересчёт кэша сигналов) выигрыш втрое меньше. Измерен один тяжёлый вызов; средний и лёгкий класс — по фикстурам (H-малая, L1), не A3.
- **Что не измерено и почему:** параллельная эффективность на **свободном** хосте («один движок за раз») — пока идёт партия, свободного хоста нет; её даёт A3 (полный тяжёлый вызов на пустом srv, окно после `tk674c-quadsS3`). Пока на свободной машине не измерено, оценки в часах стены даются в режиме **занятого хоста** (стена ∝ ЦП: каждая сэкономленная ЦП-секунда возвращается в общий пул), а ЦП-секунды — второй колонкой.

## 4. Дублирование ходов и пред-компоновка веера

Термины: **тик** — сделка ленты (то, что читает `Cursor::next_tick`); **ход** — один проход `sim_tail_e` по тикам от входа до выхода одного лота одного варианта; **позиция** — результат варианта (строка `short-trades.csv`; у позиции из двух лотов два хода).

### 4.1 Что именно повторяется (код)

`run_tick_xb` (`tick.rs:3230`) идёт по сигналам варианта в порядке времени; принятый сигнал даёт решение о входе (`entry_decision` / `mk_decision` / `xb_decision` …), затем ход лота 1 (`sim_fill_lc_e`, `tick.rs:3433`) и, при `split`, решение и ход лота 2 (`sim_fill_lc_s`, `tick.rs:3500`). Исход принятого входа зависит от: ленты монеты после `entry_ms` (общая для всех вариантов), цены входа `p0` (функция ленты), `natr` и контекста уровня `lc` (функции сигнала), параметров выхода `ExitCfg`. Портфельное состояние варианта (`busy`, `cool_until`, `open`, `gstops`, `consumed`) решает только, **какие** входы принять, но не исход принятого → **исход = чистая функция** `f(монета, entry_ms, сторона, путь-параметры ExitCfg)`. Веер — «один фактор за раз» от базы (имена вариантов: `…+e2t2+…+w270`), поэтому большинство вариантов идут по одной ленте с почти одинаковыми параметрами.

### 4.3 Дизайн пред-компоновки

**B. Память исходов (первой).** `HashMap<ключ, TickOut>` на общий вызов (шарды, 7 потоков): первый вариант считает ход, остальные берут исход.
- **B1 — ключ.** Не «поля `ExitCfg`», а **весь набор аргументов функции хода по значению + идентификатор потока монеты**: `(coin, entry_ms, p0, side, natr_e8, ex, lc, notional, entry_slip_bps, stop_px)`; для лота 2 путь лота 1 входит через `stop_px` (`s2`) и через `entry_ms` / `p0` самого лота 2. Новая гипотеза с новым полем `ExitCfg` / `LevelCtx` меняет ключ **сама** (аргументы целиком; список исключений не нужен); `ExitCfg` — только целые и `bool` (`params.rs:139-270`), `derive(Eq, Hash)` возможен. Что ход не читает ничего другого — аудит ходового кода (`tick.rs:1360–2200`: `Pos`, `Cursor`, `sim_*`): нет `static`, `thread_local`, `Atomic`, `OnceLock`, `Mutex`, `env`, `Instant`, `rand`; `&mut` только у `Pos` (self) и потока `next`; лента неизменна (`Arc<Vec<Tick>>`); `volstop::stop_pm` — чистая функция. Решения о входе (`entry_decision`, `mk_decision`, `xb_decision`, `lot2_decision_d`) тоже читают тики, но в ключ не входят и считаются как раньше (≈ 2–4 % ЦП).
- **B2 — G измерено по классам вызовов** (`ws-measure2`, ключ B1, расхождений исхода при равном ключе 0 на всех трёх): тяжёлый (H1: 1 705 вариантов × 90 монет) **1,98** по тикам (1,875 по ходам: 97 596 ходов, 52 040 различных ключей); средний (H-малая: 51 вариант × 90 монет) **1,51** (3 656 ходов, 2 506 ключей, 1,459 по ходам); лёгкий (L1: 50 вариантов) **1,45** (2 307 ходов, 1 594 ключа, 1,447 по ходам). Ходы делятся на 1,5–2, а не на 4,9; G растёт с числом вариантов в вызове. Загрузок суток = различных (монета, день) на всех трёх (768 и 747 на малых) — перераскодировки нет.
- **B3 — режим проверки**: на попадании ход всё равно считается и сверяется — 100 % в гейте (600 клеток + A3), в бою выборка ≥ 1 % попаданий с остановкой на любом расхождении (на H1 расхождений 0 из 97 596).
- В-184: B повторно использует **равное вычисление** (те же входы → тот же выход), ни один тик ни для какой гипотезы не пропущен; новая гипотеза = новое значение аргумента = другой ключ.

**A. Пучок (после B, на остатке).** Различные ходы с общим входом идут в ногу по одному срезу ленты: выборка тика и фильтр `t > entry_ms` один раз, `on_trade` у каждого. Ловушки портфеля нет: приём сигнала зависит от прежних выходов того же варианта, известных, когда прежний ход посчитан на приёме. Настоящее ограничение — **состояние между монетами**: в `run_tick_xb` это `open` (места `pc.p`, `open.len() ≥ pc.p`), `gstops` и `gpause_until` (глобальная серия стопов `s_glob` / `w_min` / `ww_min`) и общий порядок сигналов по времени; на монету — `busy`, `cool_until`, `cpause_until`, `streak`, `consumed`; по монетам делить нельзя. Остаётся деление по вариантам между потоками: оно сжимает пучок ≈ в 7 раз (при 7 потоках по 1/7 веера на поток), поэтому размер пучка надо мерить на различных ключах, а не на 29,6 хода на вход. Потолок после памяти: различные ходы / их общий ствол = **10,6× по тикам** (257,94e6 / 24,26e6) → доля снимаемой обвязки r ≤ 0,91 при пучке «весь веер в одном потоке», в реальности ниже; r — допущение, пока нет прототипа.

**C. Хранилище исходов между вызовами.** Ключ = B1 + версия кода хода (+ алиас, рычаг i). Ждёт измерения 2б: общий ключ между клетками возможен только при равном `ExitCfg`.

**D. Слияние состояний.** FAIL (критик): ломает «любая гипотеза» — новый параметр сам должен объявлять момент расхождения.

Порядок при PASS: B → A на остатке → C после 2б. Каждая ступень — отдельный коммит, до / после на H1 (хеш дерева = базе) и A3.

### 5.2 Измеренная строка (боевая смесь, стена партии при занятом хосте)

Стена партии ∝ ЦП (хост занят другими юнитами, §2.5); классы — из логов 137 вызовов (3 457 / 2 463 / 346 с); отношение ЦП LTO по ближайшей фикстуре (тяжёлый ← H1, средний ← H-малая, лёгкий ← L1): **0,763 / 0,869 / 0,952 → 81,5 ч из 100 (−18,5 %)**. **A3 (§2.5): тяжёлый вызов 539 монет на свободном хосте — стена −25,8 % при попадании кэша сигналов (63,1 → 46,8 с), −5,7 % при промахе (100,0 → 94,3 с); ЦП −26,4 % / −9,4 %.** Для владельца: «−26 % стены на одном тяжёлом вызове 539 монет (кэш сигналов попал), измерено; выигрыш партии — по счётчику первых двух партий после подмены»; первая партия после подмены платит промах кэша. ## 6. Риски и вопросы критику

1. **Полнота ключа B.** Ключ = все аргументы хода по значению; эмпирика 0 расхождений на 97 596 ходах H1; гейт — режим проверки 100 % на 600 клетках + A3, в бою ≥ 1 %. Достаточно ли?
2. **Пучок против параллелизма.** Деление по вариантам сжимает пучок ≈ в 7 раз; размер пучка меряется на остатке после B. Согласен ли критик, что A идёт только после B и только если остаток ствола (10,6× по тикам) переживёт деление?
3. **В-184.** B / C повторно используют равное вычисление; тики не пропускаются (критик: допустимо при B1).
4. **Репрезентативность.** H1 = 90 из 539 монет, один веер; доли ходов в ЦП для средних и лёгких — допущение (G по классам измерен: 1,98 / 1,51 / 1,45; A3 уточнит). Часы партии — режим занятого хоста; режим «один движок за раз» (параллельная эффективность на свободном хосте) даёт только A3.
5. **Что не посчитано.** Тики решений о входе (≈ 2–4 % ЦП); G между вызовами (2б); вклад `abort` без LTO (бинарь не мерян — не нужен для решения); PGO и его контроль ⟦v4, hold-out⟧; прототип e.

7. **Шум.** 4–8 % повтор-повтор: LTO (−23,5 %) и счётчики железа надёжны; −1,2 % (b), −4 % (glibc env), −3 % (v3) — в шуме.
