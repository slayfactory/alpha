## 4. Дублирование ходов и пред-компоновка веера

Термины: **тик** — сделка ленты (то, что читает `Cursor::next_tick`); **ход** — один проход `sim_tail_e` по тикам от входа до выхода одного лота одного варианта; **позиция** — результат варианта (строка `short-trades.csv`; у позиции из двух лотов два хода).

### 4.1 Что именно повторяется (код)

`run_tick_xb` (`tick.rs:3230`) идёт по сигналам варианта в порядке времени; принятый сигнал даёт решение о входе (`entry_decision` / `mk_decision` / `xb_decision` …), затем ход лота 1 (`sim_fill_lc_e`, `tick.rs:3433`) и, при `split`, решение и ход лота 2 (`sim_fill_lc_s`, `tick.rs:3500`). Исход принятого входа зависит от: ленты монеты после `entry_ms` (общая для всех вариантов), цены входа `p0` (функция ленты), `natr` и контекста уровня `lc` (функции сигнала), параметров выхода `ExitCfg`. Портфельное состояние варианта (`busy`, `cool_until`, `open`, `gstops`, `consumed`) решает только, **какие** входы принять, но не исход принятого → **исход = чистая функция** `f(монета, entry_ms, сторона, путь-параметры ExitCfg)`. Веер — «один фактор за раз» от базы (имена вариантов: `…+e2t2+…+w270`), поэтому большинство вариантов идут по одной ленте с почти одинаковыми параметрами.

### 4.2 Измерено

| Уровень | Что повторяется | Число | Метка |
|---|---|---|---|
| 1. Внутри вызова, между вариантами | один и тот же вход (монета, `entry_ms`) обходится разными вариантами. Мерный бинарь `ws-measure` (счётчики в `sim_tail_e`, поведение не менялось: хеш дерева вывода = базе) на H1: **97 596 ходов, 3 294 входа (29,6 хода на вход), 511 268 390 тиков в ходах; сумма максимумов длины по входу 24 259 224 тика → 21,1×** (ходы читают один и тот же участок ленты в 21 раз больше, чем длиннейший из них). Независимая оценка по времени удержания на клетке `p5cd4933c8e` (539 монет, архив, все варианты): 365 717 позиций → 10 440 входов, 35 на вход (медиана 5, максимум 1 465), Σ удержаний / Σ максимума на вход = **21,3×** — совпадает | 21,1× по тикам | изм. |
| 1б. Те же исходы | разных исходов (строка позиции целиком) 62 237 из 365 717 = **17 %**; по времени удержания **4,9×** → 80 % времени ходов повторяют исход, уже полученный другим вариантом с того же входа | 4,9× по времени | изм. |
| 2. Между вызовами одной стадии | клетки одного окна и стороны делят входы (разные куски веера на тех же сигналах): ⟦dup3: F2 по wc-S short / wc-L long / wb-S / wa-S⟧; пробный счёт на 12 первых архивах: ещё **3,5×** | ⟦F2⟧ | изм. |
| 3. Вся стадия | F12 = F1 · F2 (время удержания всех ходов / сумма максимумов по объединению входов) | ⟦F12⟧ | изм. |

Оговорки: (1) вес «время удержания» — прокси числа тиков (для 1 и 3 в ленте одной монеты число тиков пропорционально времени; подтверждено 21,1× по тикам против 21,3× по времени); (2) 21× — **потолок** общего ствола: каждый живой вариант всё равно вызывает `on_trade` / `fill_takes` на каждом тике своего хода (29,5 % ЦП на v1), общим становится только «обвязка» (`next_tick` + замыкание + цикл, 34,4 %); (3) тихие блоки (`ws_block_quiet`, строго 16 / 64 / 256 тиков): 94,1 % / 89,7 % / 81,8 % тиков лежат в блоках без событий — **не используется** (В-184: каждый тик виден стратегии), приведено только как контекст, почему `on_trade` почти всегда идёт по ветке «ничего не произошло».

### 4.3 Дизайн пред-компоновки (четыре ступени, от безопасной к рискованной)

| Ступень | Суть | Точность | Что экономит | Что нужно |
|---|---|---|---|---|
| A. Пучок (поток тиков один раз) | варианты, принявшие вход `(монета, entry_ms)`, идут в ногу по одному срезу ленты: выборка тика и фильтр `t > entry_ms` один раз, `on_trade` — у каждого варианта; исход каждого — прежняя чистая функция | байт в байт по построению (порядок вызовов на каждый вариант тот же) | «обвязку» хода: (1 − 1/N) её доли, N — вариантов в пучке (в среднем 29,6; медиана 5) | внешний цикл по сигналам → внутренний по вариантам: портфели всех вариантов в памяти одновременно (≈ 13 КБ на вариант: `busy`, `cool_until`, `cpause_until`, `streak` по 539 монетам → ≈ 22 МБ на 1 705 вариантов); тот же порядок сигналов для всех вариантов даёт ещё и общую локальность суток (сейчас `store::decode` + ZSTD 9,8 % ЦП — перераскодировка суток при `--cap-gb` и разном порядке) — **гип.** |
| B. Память исходов по ключу пути | `HashMap<(монета, entry_ms, сторона, ключ пути), TickOut>` (с блокировкой по шардам, 7 потоков): первый вариант считает ход, остальные берут исход; ключ = все поля `ExitCfg`, которые ход читает (лот 1 не читает `w2`, `e2`, `e2t`, `s2` …; лот 2 читает свои) | точна, **если ключ полон**: пропуск поля даёт молчаливо неверный исход → гейт: дифф-тест случайных вариантов с «выключенной» памятью, дерево вывода 600 клеток, список полей получается статически (`grep` по чтению `ex.<поле>` в ходе) и подтверждается тестом «поле меняется — исход меняется» | целые ходы (не только обвязку): верхняя граница 4,9× по времени ходов (уровень 1б), реально — по полноте ключа (ключ строже равенства исходов) | список прочитанных полей и счёт различных ключей по `variants.txt` (дёшево, до кода) — **гип.** |
| C. Хранилище исходов между вызовами | то же, что B, но на диске / в БД (`/data/...`), ключ + «смысловая версия» кода хода; вызов берёт готовые исходы | как B + ключ версии: правка хода инвалидирует хранилище | уровень 2: ещё до ⟦F2⟧× (по вызовам одной стадии); в боевых вызовах ходы почти всех клеток стадии на одних и тех же входах | согласование с рычагом i (ключ по исходнику, иначе каждая подмена обнуляет и хранилище); размер ≈ позиций в стадии × 200 Б; память исходов ×1,3 по TK-683 (слабо) считалась на уровне 1б без F2 — **гип.** |
| D. Слияние состояний | варианты с равным `Pos` идут одним состоянием до расхождения параметров | требует знания «до какого момента» параметры не влияют → зависит от гипотез | вариант для критика и владельца | **не рекомендуется** (ломает «любая гипотеза»: новый параметр выхода должен сам объявлять момент расхождения) |

Порядок работ при PASS: A (точна по построению) → B (после списка полей) → C (если F2 подтвердится на боевых клетках) — каждая ступень отдельным коммитом, до / после на H1, хеш дерева = базе.
