## 1. Зачем

Решение владельца В-175 (дословно): «ок тогда просто удаляй традфи» / «все по традфи». TradFi-контракты (236 из 775 в окне 01.07–13.11) уходят из П-42; состав — 539 крипто-контрактов. Клетки на 775 контрактах (пары L-302, тройки L-303, split L-305 / L-320, четвёрки L-315, единички L-321…L-326) остаются в летописи как история состава 775 и на новом составе выводом не служат. Остановлено на границе пакета 22.11 18:35 UTC: `tk674bs3q-chain` (тройки с split: лонг 704 из 704 клеток на диске, шорт 400 из 4 264; в БД не записаны) и `tk674bx-chain` (пары с осями TK-680, PS-973, 0 клеток). Поправки PS-969 (потолки четвёрок с split и дельты троек) и PS-973 на составе 775 не исполняются; их правила и потолки переносятся сюда без изменений.

## 2. Состав и способ (точная модель)

Состав `c539` = список h775 (`/data/p42-tk621/universe/symbols-all.txt`) минус список TradFi В-175 (`contracts.csv` `tradfi = 1` ∪ exchangeInfo `TRADIFI_PERPETUAL`); файл списка — `/data/p42-tk621/universe/symbols-crypto.txt`, sha256 печатается в записи летописи до первого счёта. Движок получает этот список аргументом `--symbols` (как сейчас получает h775): TradFi-монет нет ни среди кандидатов, ни в портфеле, лимит позиций считает движок. В БД летописи клетки пишутся с вселенной `c539` — отдельное пространство ключей, с клетками h775 не смешиваются; «есть в БД» на старте = 0.

Почему не столбец-фильтр `tradfi.le_v0` для всего перебора: таблица фильтров (`--ftab`) привязана к кандидатам базового уровня по `sig_ms`, у кандидата без строки фильтр «проходит» — на осях, меняющих кандидатов (оси уровня, `e`, ключи сигнала; сейчас это запреты «столбец × ось уровня» и т. п., 190 / 238 пар), TradFi-сигналы остались бы в счёте. Список монет действует на всех осях. **Сверка двух способов до счёта карты (гейт):** якорь стороны на `c539` списком монет против якоря TK-680 с фильтром `tradfi.le_v0` на h775 — наборы сделок должны совпасть (ключи сделок и P&L); расхождение — разбор причины до любого счёта, не выбор способа по результату.

**Признаки по монете и зависящие от состава (критик, FIX a).** Признаки осей карты (`f12` и столбцы TK-654 / TK-671 / TK-680: `n24`, `tpm60`, `cons60`, `zv6h`, `ok10_d*`) считаются по самой монете (или по BTC: `btc_mv5`): ни доли по вселенной, ни ранга в срезе; меньший состав меняет только набор кандидатов и слоты портфеля, не значения признаков. От состава зависит одна ось — `cosig15` (число других монет с сигналом базы той же стороны в (t − 15 мин, t), §13.73.13): на `c539` она считается только по сигналам крипто-монет и пересчитывается (TK-680) до счёта единичек; столбцы «рынка» `peers7` / `peer_sig30` в оси перебора не входят — войдут, определяются на `c539` до счёта.

## 3. Якоря и охраны

Якоря — те же строки, что в §13.73.2: лонг стоп 3 %, шорт стоп 4 % (шорт входит двумя частями, e2 = 0,05), считаются на `c539` заново (G-base на новом составе; строк со стопом 5 % нет, В-173). Ориентир до счёта (В-175, из готовых сделок h775 простым исключением монет, не прогон движка: лимит позиций пересчитается): лонг 296 сделок, +326 $; шорт 172 сделки, +134 $.

Охрана (а) §13.73 записана в абсолютных числах (n ≥ 150, в месяце ≥ 15). На новом составе сделок меньше по построению (шорт ≈ 172 у якоря): при прежнем пороге почти любая клетка шорта с фильтром не пройдёт охрану, и карта шорта будет пустой не из-за результата. **Назначается до счёта:** порог (а) масштабируется числом сделок якоря, округление вверх: n_min = 150 × n якоря c539 / n якоря h775 (428 лонг / 319 шорт — база §13.73.2, PS-955; 296 + 132 и 172 + 147 по В-175), в месяце — 15 × то же отношение; при ориентире выше — лонг 104 и 11, шорт 81 и 9; точные числа фиксируются записью летописи после счёта якорей и до счёта остальных клеток, по формуле, без выбора (критик: PASS, масштабирование сохраняет относительную строгость охраны, прежние 150 / 15 пустили бы карту шорта по построению). Остальные охраны (б)–(д), плато (г), правило `pick` — без изменений. Меньше сделок — шире шум: в отчёте рядом с каждой строкой число сделок и шум выбора.

## 6. Чтение, счётчик, шум

Как §13.73.2–§13.73.15: ставка 500 $, маржа 250 $; R:R и убыток на стоп первыми (у шорта «только A» / «A + B» раздельно), Σ $, $ на сделку, число сделок, годовой Шарп по суткам, просадка ($, % маржи, % от Σ), перехай, якорь рядом с каждой строкой; без медиан; торгуется одна линия. Основное m стороны = клетки стороны на `c539` в БД на момент чтения + клетки h775 той же стороны в БД (те же месяцы, состав `c539` выбран по результату h775 — одна цепочка отбора, правило навыка «счётчик включает весь перебор»; критик FIX b); рядом справочно печатается m только по `c539`. Шум выбора ≈ σ·√(2 ln m) — по основному m. Аудит TK-682 в силе: пороги `_q` и квантили столбцов — «подобран на этих данных» (пороги пересчитываются на кандидатах `c539`, файлы порогов с sha256 — до счёта клеток); SHARP не читается; повторы наборов сделок — один раз; мёртвые ключи при `pb = 1` — не оси; у `bm3` стопы после 1-го тейка отдельно (L-319). Состав `c539` выбран по результату на этих данных (TradFi убыточен у лонга: 132 сделки, −71 $) — все строки нового состава несут пометку «состав выбран на этих данных».
